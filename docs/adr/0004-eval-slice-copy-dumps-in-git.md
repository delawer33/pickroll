# Eval-срез: сжатые COPY-дампы в git, загрузка только в пустую базу

Eval ответов обязан давать одинаковый результат на машине разработчика и в CI, а полная база (1,5 млн строк Box Score, корпус Wikipedia с эмбеддингами, часы индексации и платные вызовы эмбеддера) в CI недоступна. Поэтому данные для eval — **Eval-срез**: полные сезоны (последний сезон базы, один сезон до трёхочковых, сезоны из вопросов Золотого набора), игроки и команды целиком, rulebook целиком и статьи Wikipedia из `expect_documents` Золотого набора, всё с готовыми эмбеддингами.

Решения:

- **Формат — `COPY ... TO STDOUT` в text-формате, сжатый gzip, по файлу на таблицу + `manifest.json`** (счётчики строк, sha256, колонки, ревизия Alembic, модель эмбеддингов). Не SQL-INSERT и не JSON: тот же формат, которым seed грузит датасет; вектор едет текстом и возвращается как есть, эмбеддер не вызывается. Дамп детерминирован (gzip без mtime, сортировка по ключу) — пересборка на тех же данных не даёт диффа в git.
- **Состав выводится из Золотого набора, а не дублируется в конфиге.** Сезоны берутся из `question`, статьи — из `expect_documents`; в `slice.yaml` лежит только то, чего из набора не вывести. Добавили вопрос — пересобрали срез, и он в нём. Устаревший срез (набор дописали, срез нет) ловится по манифесту до первого платного вызова.
- **В git, пока ≤ 15 МБ;** сверх бюджета сборщик падает и срез выкладывается asset'ом GitHub Release (CI скачивает его перед прогоном). Дампы — бинарники, и каждая пересборка добавляет их в историю заново: поэтому срез пересобирается по необходимости, а не на каждый коммит.
- **Загрузчик грузит только в пустую базу** (или в ту, где срез уже лежит) и отказывается иначе. `answer_eval --slice` можно запускать с любым `DATABASE_URL` — полная локальная база разработчика не будет тихо перемешана со срезом. Загрузка — одна транзакция, миграции — штатный `alembic upgrade head`, а не копия схемы в дампе.
- **Производные данные не выгружаются, а пересчитываются** хуком `eval_slice/derived.py` теми же командами, что и на полной базе (Статистические отпечатки подключаются сюда в спринте 3.5; Перцентили считаются запросом на лету). Иначе срез хранил бы вторую копию логики расчёта.

Отвергнуто:

- **`pg_dump` среза** — тянет схему и версию Postgres за собой и ломается о миграции, выполненные после сборки; COPY-дамп с явным списком колонок переживает добавление колонок с default'ом.
- **Синтетические данные** — eval на выдуманной статистике не ловит ровно то, ради чего он нужен (реальные имена-однофамильцы, пустые метрики ранних эпох, реальный корпус).
- **Срез с подмножеством игроков** — резолвер имён (`Джонсон`) увидел бы меньше кандидатов, чем на полной базе, и вопросы про неоднозначность перестали бы быть теми же вопросами.

Известное расхождение: Инструмент без сезона (`get_player_stats` без `season` — карьера) на срезе считает только по сезонам среза. Вопросы Золотого набора, привязанные к сезону, совпадают с полной базой побайтово; карьерные — нет, и расхождение в ±1 вопрос по категории biography допустимо (см. `docs/deferred.md`).
